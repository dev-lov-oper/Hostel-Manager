1 What is the Template Method Pattern?

The Template Method is a Behavioral Design Pattern defined in the Gang of Four (GoF) catalog. It defines the skeleton of an algorithm in an abstract base class, deferring certain steps to subclasses. Subclasses can override specific steps of the algorithm without changing its overall structure or execution order.

GoF Definition

"Define the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure."

— Gamma, Helm, Johnson, Vlissides (Design Patterns: Elements of Reusable Object-Oriented Software, 1994)

Key Characteristics

  • The template method itself is declared final — subclasses cannot alter the sequence of steps.
  • Abstract steps (primitive operations) must be implemented by every concrete subclass.
  • Optional hook methods provide default behavior that subclasses may override.
  • The Hollywood Principle applies: "Don't call us, we'll call you" — the base class controls the flow and calls subclass methods at the right time.

2 Why Template Method in HostelHub?

In a hostel management system, the Check-In and Check-Out processes share a remarkably similar lifecycle structure: both require identity verification, allocation status validation, room inspection, key/dues handling, and database state updates. However, the details of each step differ significantly:

Concern Check-In Check-Out
Identity Check Verify enrollment & eligibility Verify departure clearance
Required Allocation State ALLOCATED or CHECKED_OUT CHECKED_IN
Room Inspection Baseline inventory — record initial condition Damage assessment against baseline
Key Handling Issue key to student Collect key from student
Dues Verify semester fees paid Verify no outstanding mess/utility dues; issue No-Dues Certificate
Database Update Status → CHECKED_IN Status → CHECKED_OUT; decrement room occupancy

Without the Template Method pattern, this would result in duplicated control flow logic across both processes. The pattern eliminates this duplication by encoding the invariant 5-step sequence once in HostelProcess.executeProcess() and letting each subclass supply its own step implementations.

4 The 5-Step Invariant Process Sequence

The template method executeProcess() enforces a strict, fail-fast sequential pipeline. If any step returns false, the entire process halts immediately and records a failure. Here is the fixed sequence:

1 verifyIdentityAndEligibility(studentId)
Purpose: Confirm the student's identity and eligibility.
Check-In: Validates the student's enrollment ID exists in the institutional database.
Check-Out: Verifies the student has departure clearance and active enrollment status.
Fail condition: studentId ≤ 0 (invalid student reference).
2 verifyAllocationStatus(allocationId)
Purpose: Ensure the room allocation is in the correct state for this operation.
Check-In: Allocation must be in ALLOCATED or CHECKED_OUT state (fresh allocation or re-entry).
Check-Out: Allocation must be in CHECKED_IN state (student must be currently residing).
Database query: Uses ProcessDAO.isAllocationInState() to query the room_allocations table.
3 inspectRoomAndInventory(roomId)
Purpose: Physical inspection of the room and its inventory items.
Check-In: Records the baseline inventory — lists all amenities (Bed Frame, Study Desk, Chair, Wardrobe, Ceiling Fan, Smart Lock) and confirms zero pre-existing damage. This baseline is used for comparison during check-out.
Check-Out: Performs a damage assessment — compares current room condition against the check-in baseline. Checks fixtures, wall paint, electrical sockets, and furniture for any damage.
Data source: Reads amenity list from RoomDAO.findRoomById().
4 handleKeyAndDues(allocationId)
Purpose: Manage physical key handover and financial clearance.
Check-In: Issues a unique physical key tag (KEY-ALLOC-<id>-ENTRY) to the student and verifies semester hostel fees are settled (£0.00 outstanding).
Check-Out: Collects the key tag back from the student, verifies that all mess & utility balances are zero, and issues an institutional "No Dues Certificate".
5 updateDatabaseStatus(allocationId, roomId)
Purpose: Persist the final state transition in the database.
Check-In: Updates allocation status to CHECKED_IN via ProcessDAO.updateAllocationState().
Check-Out: Executes a transactional operation via ProcessDAO.releaseBed(): (a) updates allocation to CHECKED_OUT, (b) decrements the room's current_occupancy by 1.
Transaction safety: The check-out uses conn.setAutoCommit(false) with explicit commit() / rollback().
Fail-Fast Behavior

If any step (1 through 4) returns false, the template method immediately halts, logs the failure reason, calls recordFailure() to persist an audit trail, and returns false — steps after the failure point are never executed. This guarantees no partial state corruption.

5 Source Code — Abstract Class: HostelProcess.java

This is the heart of the pattern. The class declares the final template method and the abstract primitive operations that subclasses must implement.

JAVA
package app.patterns.template;  

import java.util.ArrayList;
import java.util.List;

/**
 * Template Method Pattern: Abstract Hostel Lifecycle Process
 */
public abstract class HostelProcess {

    protected final List<String> executionLog = new ArrayList<>();

    /**
     * Final Template Method defining the fixed process sequence.
     */
    public final boolean executeProcess(int allocationId, int studentId, int roomId) {
        executionLog.clear();
        logStep("Starting process sequence for Allocation ID: " + allocationId);

        try {
            if (!verifyIdentityAndEligibility(studentId)) {
                logStep("FAILED: Identity verification failed.");
                recordFailure(allocationId, "Identity verification failed.");
                return false;
            }

            if (!verifyAllocationStatus(allocationId)) {
                logStep("FAILED: Allocation status invalid.");
                recordFailure(allocationId, "Allocation status invalid.");
                return false;
            }

            if (!inspectRoomAndInventory(roomId)) {
                logStep("FAILED: Room and inventory inspection failed.");
                recordFailure(allocationId, "Room inspection failed.");
                return false;
            }

            if (!handleKeyAndDues(allocationId)) {
                logStep("FAILED: Key/Dues clearance failed.");
                recordFailure(allocationId, "Key/Dues clearance failed.");
                return false;
            }

            updateDatabaseStatus(allocationId, roomId);
            logStep("COMPLETED: Process completed successfully.");
            recordSuccess(allocationId);
            return true;

        } catch (Exception e) {
            logStep("ERROR: Exception occurred - " + e.getMessage());
            recordFailure(allocationId, e.getMessage());
            return false;
        }
    }

    // Step 1: Subclass-defined verification
    protected abstract boolean verifyIdentityAndEligibility(int studentId);

    // Step 2: Subclass-defined allocation state check
    protected abstract boolean verifyAllocationStatus(int allocationId);

    // Step 3: Room/Inventory condition check
    protected abstract boolean inspectRoomAndInventory(int roomId);

    // Step 4: Keys handover / Return and Dues clearance
    protected abstract boolean handleKeyAndDues(int allocationId);

    // Step 5: Database state updates
    protected abstract void updateDatabaseStatus(int allocationId, int roomId);

    // Audit Record Hooks
    protected abstract void recordSuccess(int allocationId);
    protected abstract void recordFailure(int allocationId, String reason);

    protected void logStep(String message) {
        executionLog.add(message);
    }

    public List<String> getExecutionLog() {
        return List.copyOf(executionLog);
    }
}

Line-by-Line Explanation

LinesWhat It DoesWhy It Matters
11 Declares executionLog as a protected final List<String> Both subclasses inherit this shared execution log. The final keyword prevents reassignment but allows mutation (adding entries). Every step appends descriptive messages here for audit tracing.
16 public final boolean executeProcess(...) The template method. Marked final so subclasses cannot override the algorithm's skeleton — they can only fill in individual steps. This is the core of the pattern.
17 executionLog.clear() Resets the log at the start of each execution so that if the same object is reused, previous logs don't leak into the new run.
21–43 Sequential if (!stepN(...)) guards Each step is called in strict order. If any returns false, the method logs the failure, records it in the database, and returns false immediately. This implements fail-fast sequencing.
45–48 Success path: updateDatabaseStatus → logStep → recordSuccess → return true Only reached if all 4 validation steps passed. Persists the final state change, logs completion, and saves a success audit record.
50–54 Exception handler Catches any unexpected runtime exception (e.g., database I/O failure), records it in the audit log, and returns false — ensuring the process never silently crashes.
58–75 7 protected abstract methods These are the primitive operations that subclasses must implement. They include the 5 process steps plus 2 audit hooks (recordSuccess and recordFailure).
77–79 logStep() — concrete hook A non-abstract helper method that subclasses use to append descriptive messages to the execution log. Subclasses could override it but don't need to — it has a useful default implementation.
81–83 getExecutionLog() Returns an immutable copy of the log via List.copyOf(). This prevents external code from tampering with the internal log after the process completes.

6 Source Code — Concrete Class: CheckInProcess.java

This subclass fills in all 7 abstract methods with check-in–specific logic.

JAVA
package app.patterns.template;

import app.model.Room;
import app.patterns.singleton.ProcessDAO;
import app.patterns.singleton.RoomDAO;

public class CheckInProcess extends HostelProcess {

    private final ProcessDAO repository = ProcessDAO.getInstance();
    private final RoomDAO roomRepository = RoomDAO.getInstance();

    @Override
    protected boolean verifyIdentityAndEligibility(int studentId) {
        logStep("Step 1 [Identity]: Verifying student ID card #" + studentId
                + " against institutional enrollment database...");
        return studentId > 0;
    }

    @Override
    protected boolean verifyAllocationStatus(int allocationId) {
        logStep("Step 2 [Status]: Checking allocation #" + allocationId
                + " is in 'ALLOCATED' or 'CHECKED_OUT' state...");
        boolean valid = repository.isAllocationInState(allocationId, "ALLOCATED")
                || repository.isAllocationInState(allocationId, "CHECKED_OUT");
        if (!valid) {
            logStep("FAILED: Allocation is neither 'ALLOCATED' nor previously cleared 'CHECKED_OUT'.");
        }
        return valid;
    }

    @Override
    protected boolean inspectRoomAndInventory(int roomId) {
        Room room = roomRepository.findRoomById(roomId);
        String items = (room != null && room.getAmenities() != null && !room.getAmenities().isEmpty())
                ? String.join(", ", room.getAmenities())
                : "Bed Frame, Ergonomic Study Desk, Chair, Wardrobe, Ceiling Fan, Smart Lock";
        String roomNum = room != null ? room.getRoomNumber() : "#" + roomId;

        logStep("Step 3 [Inventory]: Inspecting Room " + roomNum
                + " against Prototype template blueprint.");
        logStep("Baseline Inventory verified intact: [" + items
                + "]. Zero pre-existing damage recorded.");
        return true;
    }

    @Override
    protected boolean handleKeyAndDues(int allocationId) {
        logStep("Step 4 [Keys & Dues]: Assigned physical key tag [KEY-ALLOC-"
                + allocationId + "-ENTRY].");
        logStep("Hostel fee ledger verified: Semester fees settled (₹0.00 outstanding dues).");
        return true;
    }

    @Override
    protected void updateDatabaseStatus(int allocationId, int roomId) {
        logStep("Step 5 [Persistence]: Updating allocation #" + allocationId
                + " to 'CHECKED_IN' in database...");
        repository.updateAllocationState(allocationId, "CHECKED_IN");
    }

    @Override
    protected void recordSuccess(int allocationId) {
        repository.saveProcessRecord(allocationId, "CHECK_IN", "COMPLETED",
                String.join("\n", executionLog));
    }

    @Override
    protected void recordFailure(int allocationId, String reason) {
        repository.saveProcessRecord(allocationId, "CHECK_IN", "FAILED",
                String.join("\n", executionLog));
    }
}

Key Implementation Details

  • Step 1 (verifyIdentityAndEligibility): Simply checks studentId > 0. In a production system, this would query the enrollment database — here it demonstrates the verification hook.
  • Step 2 (verifyAllocationStatus): Queries the database via ProcessDAO.isAllocationInState() to confirm the allocation is either ALLOCATED (freshly assigned) or CHECKED_OUT (student re-checking in after a break).
  • Step 3 (inspectRoomAndInventory): Fetches the room from RoomDAO, reads its amenities list, and logs the baseline inventory. If no amenities are stored, falls back to a hardcoded default list.
  • Step 4 (handleKeyAndDues): Issues a key tag with a unique identifier format KEY-ALLOC-{id}-ENTRY and logs that semester fees are settled.
  • Step 5 (updateDatabaseStatus): Calls ProcessDAO.updateAllocationState(allocationId, "CHECKED_IN") to persist the state transition.
  • Audit hooks: Both recordSuccess and recordFailure call ProcessDAO.saveProcessRecord() with the full execution log, ensuring every process run is traceable in the process_logs and hostel_process_records tables.

7 Source Code — Concrete Class: CheckOutProcess.java

This subclass provides the check-out–specific implementations.

JAVA
package app.patterns.template;

import app.model.Room;
import app.patterns.singleton.ProcessDAO;
import app.patterns.singleton.RoomDAO;

public class CheckOutProcess extends HostelProcess {

    private final ProcessDAO repository = ProcessDAO.getInstance();
    private final RoomDAO roomRepository = RoomDAO.getInstance();

    @Override
    protected boolean verifyIdentityAndEligibility(int studentId) {
        logStep("Step 1 [Authorization]: Verifying student departure clearance "
                + "and enrollment status for Student #" + studentId + "...");
        return studentId > 0;
    }

    @Override
    protected boolean verifyAllocationStatus(int allocationId) {
        logStep("Step 2 [Status]: Checking allocation #" + allocationId
                + " is currently 'CHECKED_IN'...");
        boolean valid = repository.isAllocationInState(allocationId, "CHECKED_IN");
        if (!valid) {
            logStep("FAILED: Allocation is not 'CHECKED_IN'. "
                    + "Student must be checked in first.");
        }
        return valid;
    }

    @Override
    protected boolean inspectRoomAndInventory(int roomId) {
        Room room = roomRepository.findRoomById(roomId);
        String items = (room != null && room.getAmenities() != null && !room.getAmenities().isEmpty())
                ? String.join(", ", room.getAmenities())
                : "Bed Frame, Ergonomic Study Desk, Chair, Wardrobe, Ceiling Fan, Smart Lock";
        String roomNum = room != null ? room.getRoomNumber() : "#" + roomId;

        logStep("Step 3 [Damage Assessment]: Inspecting Room " + roomNum
                + " against baseline check-in inventory.");
        logStep("Assessing fixtures [" + items
                + "]: 0 damages found. Wall paint, electrical sockets & furniture certified intact.");
        return true;
    }

    @Override
    protected boolean handleKeyAndDues(int allocationId) {
        logStep("Step 4 [Keys & Dues]: Physical key tag [KEY-ALLOC-"
                + allocationId + "] returned to Warden.");
        logStep("Accounts verification: Mess & utility balance ₹0.00. "
                + "Institutional 'No Dues Certificate' issued.");
        return true;
    }

    @Override
    protected void updateDatabaseStatus(int allocationId, int roomId) {
        logStep("Step 5 [Persistence]: Releasing bed for allocation #"
                + allocationId + " (Status -> CHECKED_OUT, Room occupancy -1)...");
        repository.releaseBed(allocationId, roomId);
    }

    @Override
    protected void recordSuccess(int allocationId) {
        repository.saveProcessRecord(allocationId, "CHECK_OUT", "COMPLETED",
                String.join("\n", executionLog));
    }

    @Override
    protected void recordFailure(int allocationId, String reason) {
        repository.saveProcessRecord(allocationId, "CHECK_OUT", "FAILED",
                String.join("\n", executionLog));
    }
}

Key Differences from CheckInProcess

  • Step 2: Requires CHECKED_IN state (not ALLOCATED) — a student must already be residing in the room to check out.
  • Step 3: Performs a damage assessment instead of recording baseline — inspects every fixture and reports damage count.
  • Step 4: Collects the key back (instead of issuing it) and verifies all financial dues before issuing a No Dues Certificate.
  • Step 5: Calls ProcessDAO.releaseBed() which is a transactional operation — it both updates the allocation status to CHECKED_OUT and decrements the room's current_occupancy by 1, wrapped in a database transaction with rollback support.

9.2 ProcessService (Client Facade)

The ProcessService acts as a simple facade that the REST API layer uses to invoke check-in or check-out. It creates the appropriate HostelProcess subclass and calls the template method.

JAVA
package app.service;

import app.patterns.template.CheckInProcess;
import app.patterns.template.CheckOutProcess;
import app.patterns.template.HostelProcess;

public class ProcessService {

    public boolean executeCheckIn(int allocationId, int studentId, int roomId) {
        HostelProcess process = new CheckInProcess();
        return process.executeProcess(allocationId, studentId, roomId);
    }

    public boolean executeCheckOut(int allocationId, int studentId, int roomId) {
        HostelProcess process = new CheckOutProcess();
        return process.executeProcess(allocationId, studentId, roomId);
    }
}
Pattern Collaboration

The Template Method pattern collaborates with two other patterns in this system:

  • Singleton: ProcessDAO.getInstance() and RoomDAO.getInstance() ensure that all process instances share the same database connection manager.
  • Prototype: Step 3 references the room's amenity list, which may have been cloned from a RoomPrototype template via the Prototype pattern.

JAVA
// From RestApiServer.java — handleExecuteProcess()
private void handleExecuteProcess(HttpExchange exchange) throws IOException {
    ExecuteProcessRequest req = mapper.readValue(
            exchange.getRequestBody(), ExecuteProcessRequest.class);

    // Demonstrates Template Method Pattern:
    HostelProcess process = "CHECK_OUT".equalsIgnoreCase(req.processType())
            ? new CheckOutProcess()
            : new CheckInProcess();

    boolean success = process.executeProcess(
            req.allocationId(), req.studentId(), req.roomId());
    List<String> logSteps = process.getExecutionLog();

    Map<String, Object> data = new HashMap<>();
    data.put("processType", req.processType().toUpperCase());
    data.put("success", success);
    data.put("allocationId", req.allocationId());
    data.put("studentId", req.studentId());
    data.put("roomId", req.roomId());
    data.put("executionSteps", logSteps);

    SseBroadcaster.getInstance().broadcast("PROCESS_EXECUTED",
            mapper.writeValueAsString(data));
    sendJsonResponse(exchange, 200, ApiResponse.ok(
        success
            ? "Process sequence executed successfully (Template Method Pattern)"
            : "Process sequence rejected by Template Method validation",
        data
    ));
}

How the Handler Works

  1. Deserialize the incoming JSON into an ExecuteProcessRequest record.
  2. Polymorphic instantiation: Based on processType, create either a CheckOutProcess or CheckInProcess. The variable type is HostelProcess (the abstract parent), demonstrating programming to an interface, not an implementation.
  3. Execute the template method via process.executeProcess(). The base class controls the flow; the concrete subclass supplies the step logic.
  4. Retrieve the execution log via process.getExecutionLog() for the API response.
  5. Broadcast a Server-Sent Event (PROCESS_EXECUTED) to all connected SSE clients for real-time UI updates.
  6. Respond with a JSON payload containing the success/failure status and the complete execution step trace.

13 Unit Testing the Template Method

The test validates that the template method correctly handles invalid inputs and records failure in the execution log.

JAVA
package app.patterns;

import app.patterns.template.CheckInProcess;
import app.patterns.template.HostelProcess;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

public class TemplateTest {

    @Test
    public void testCheckInWorkflowFailsForInvalidStudentId() {
        HostelProcess checkIn = new CheckInProcess();

        // Student ID = 0 (Invalid)
        boolean result = checkIn.executeProcess(1, 0, 101);

        assertFalse(result);
        assertTrue(checkIn.getExecutionLog().stream()
                .anyMatch(log -> log.contains("FAILED")));
    }
}

What the Test Verifies

  1. A CheckInProcess is instantiated (concrete subclass) but assigned to the abstract type HostelProcess — demonstrating polymorphism.
  2. executeProcess(1, 0, 101) is called with studentId = 0 (invalid).
  3. The template method calls verifyIdentityAndEligibility(0), which returns false because 0 ≤ 0.
  4. The method immediately halts, logs "FAILED", and returns false.
  5. assertFalse(result) confirms the process failed.
  6. The log is inspected to ensure at least one entry contains "FAILED".

14 Key Design Decisions & OOP Principles

PrincipleHow It's Applied
Open/Closed Principle The algorithm (executeProcess) is closed for modification (marked final) but open for extension — you can create new subclasses (e.g., TransferProcess, EmergencyEvacuationProcess) without touching the base class.
Hollywood Principle "Don't call us, we'll call you." The base class (HostelProcess) controls when each subclass method is invoked. Subclasses never call executeProcess() or decide the step order themselves.
DRY (Don't Repeat Yourself) The 5-step fail-fast logic, exception handling, and logging infrastructure are written once in HostelProcess. Both subclasses inherit it without duplication.
Liskov Substitution Wherever HostelProcess is expected (e.g., in ProcessService, RestApiServer), either CheckInProcess or CheckOutProcess can be used interchangeably without breaking behavior.
Single Responsibility Each class has one job: HostelProcess manages the algorithm skeleton; CheckInProcess handles check-in specifics; CheckOutProcess handles check-out specifics; ProcessDAO handles persistence.
Encapsulation All abstract methods are protected — they cannot be called directly by external code. The only public entry point is the template method itself. The execution log is returned as an immutable copy.
Separation of Concerns Business logic (step implementations) is separated from control flow (template method), persistence (ProcessDAO), and API handling (RestApiServer). Each layer is independently testable and modifiable.

15 Conclusion

The Template Method pattern in HostelHub provides a clean, maintainable, and extensible architecture for managing hostel lifecycle processes. By encoding the invariant 5-step sequence in a final template method and delegating step-specific behavior to subclasses, the system achieves:

  • Zero code duplication between Check-In and Check-Out workflows.
  • Guaranteed process integrity — the step order can never be accidentally changed or skipped.
  • Fail-fast safety — any failed step halts the entire pipeline before partial state corruption.
  • Complete audit traceability — every step is logged, and final outcomes are persisted to the database.
  • Easy extensibility — adding a new process (e.g., room transfer, emergency evacuation) requires only creating a new subclass; the template method and infrastructure remain untouched.
